# **Master Backlog: Bristol Regional Food Network**

*This document helps the development team understand what to build, when to build it, and exactly how it will be evaluated without referencing multiple documents. The tasks are ranked based on importance as well as priority, include dependencies, user stories and acceptance criteria.*

| Rank | Feature Name | MoSCoW Priority | Dependency | User Story | Acceptance Criteria |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1** | Product Catalog & Search | Must Have | Core foundation: Customers cannot have a multi-vendor cart without finding produce first. | As a customer, I want to browse products organized by categories and use a search bar to find specific items. | Features a category navigation menu and a keyword search bar. |
| **2** | Multi-Vendor Shopping Cart | Must Have | Prerequisite for checkout: Must combine items from different vendors into a single session before payment. | As the customer, I want to purchase items from multiple vendors with a single transaction. | Shopping cart accepts items from various different vendors and processes a single payment for the total. |
| **3** | Secure Single-Transaction Checkout | Must Have | Core operational process: Payment must succeed before any order details can be routed to vendors. | As a customer, I want my multi-vendor checkout to process securely while automatically handling the network's 5% commission in the background. | The Camunda checkout process successfully routes the transaction through a mock payment gateway. |
| **4** | Automated 5% Commission Deduction | Must Have | Must be calculated in the engine immediately after successful checkout and before distributing funds. | *(Combined with secure checkout)* As a customer, I want the system to automatically handle the network's 5% commission. | Automatically calculates the 5% network deduction. |
| **5** | Split Delivery/Collection Instructions | Must Have | Post-checkout: Customers must be notified how they will receive their order from the different vendors they purchased from. | As a customer, I want clear instructions on delivery and collection for each vendor in my multi-vendor order so I know how to get my items. | The checkout confirmation screen and data flow clearly split the order by supplier and detail specific delivery/collection arrangements for each. |
| **6** | Partial Order Failure (Exception Handling) | Must Have | Required for advanced Camunda modeling: Proves that the system can issue partial refunds if a single vendor rejects a part of a multi-vendor order. | As a customer, I want my order to proceed even if one vendor in my multi-vendor cart rejects their portion, so I receive the rest of my groceries and an automatic partial refund. | The Camunda process utilizes boundary error events to catch a single vendor's rejection, issues a partial refund for that specific amount, and allows the remaining vendors' fulfillment processes to continue. |
| **7** | Product Traceability & Safety Data | Must Have | Enhances the catalog (Rank 1): Displays additional details like harvest dates and allergen warnings. (required) | As a customer, I want to see harvest dates, farm origins, organic certification and allergen warnings clearly for each item. | Product detail pages display mandatory fields for harvest date, origin, allergen info, and certification status. |
| **8** | Consolidated Delivery Synchronization | Should Have | Built on top of basic logistics (Rank 5): Calculates a single delivery window based on the 48-hour minimum lead time across multiple farms. | As a customer ordering from three different farms, I want the system to calculate a single, synchronized delivery window so I do not receive three separate drop-offs at different times. | The process engine holds the customer's delivery notification until all individual vendor preparation timers (minimum 48 hours) have elapsed, calculating the latest possible dispatch time for a consolidated route. |
| **9** | Direct Vendor Communication | Should Have | Requires Secure Single-Transaction Checkout (Rank 3) to accurately link the customer's completed order to the correct producer. | As a customer, I want access to rapid communication channels on the storefront in case I have food safety or quality concerns. | A contact or report feature is integrated into the operational process, directly linking the customer's order to the specific producer. |
| **10** | Postcode-based "Food Miles" | Could Have | Extra sustainability feature: Added to the checkout flow only after the core payment routing (Rank 3) is stable. | As a customer, I want to see the "food miles" for my local produce delivery to understand the environmental impact. | The checkout process includes a step that calculates the physical distance between the customer's entered postcode and the farm's origin postcode. |
| **11** | Dynamic Surplus Integration | Could Have | Complex case for waste reduction: Requires the core catalog (Rank 1) and checkout routing (Rank 3) to be fully stable. | As a customer browsing late in the day, I want to see discounted surplus items so I can purchase affordable food while helping producers reduce waste. | The Camunda process incorporates a timer event that automatically applies a set discount percentage to remaining perishable stock in the system. |
